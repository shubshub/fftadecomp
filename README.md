Advance* (USA, `AFXE`), ready to start decompiling.

The analysis, split and matching harness live in **fftadecomp-kit**; they
produced everything here from the ROM in this directory. No third-party decomp
tool output is used.

### Keeping these numbers current

The block above — badges and table — is generated, not typed. Recompute and
rewrite it with:

```sh
python ../fftadecomp-kit/tools/status.py --write          # from the match reports
python ../fftadecomp-kit/tools/status.py --write --verify # recompile everything first
python ../fftadecomp-kit/tools/status.py --check          # exit 1 if stale (CI does this)
```

or `make status` / `make verify`. Two GitHub Actions workflows keep it honest:
`status` fails a push if the committed numbers are stale and refreshes them
weekly, and `matches` refuses any function in `src/` that lacks a match report
saying byte-identical — which is the repo rule, enforced.

The badges are **static** shields.io URLs (`/badge/label-message-color`) rather
by shields.io itself, which cannot read a private repository, so they render as
*resource not found* here; static ones render for any visibility and are
rewritten from the numbers every time the block is regenerated. `status.py
--badges` still writes the endpoint JSON to `docs/badges/` if the repo ever
goes public and you want the self-updating form.

### Two things about this ROM

**1. The cartridge header passes validation.**

* The Nintendo logo at `0x08000004`-`0x0800009F` matches the expected logo.
* The computed and stored header checksum are both `0x89`.

Earlier reports of 148 differing logo bytes and a computed checksum of `0x85`
were analyzer defects, not evidence of ROM damage. The corrected kit validates
both fields. A copy named `Final Fantasy Tactics Advance (USA, Australia).gba`
was also checked byte-for-byte against this baserom and is identical. Compare
SHA-1 against the value above before starting a matching build.

**2. The main code region is the first ~1.3 MiB, but executable code also exists later.**

The layout is not "text, then rodata, then gfx" like an unstripped build:

| ROM range | Size | What it is |
|---|---|---|
| `0x08000000`-`0x080000C0` | 192 B | cartridge header |
| `0x080000C0`-`0x08150000` | **1.31 MiB** | **code region** — Thumb-dominant, data and literal pools interleaved |
| `0x08150000`-`0x08A39820` | ~9.5 MiB | mostly assets: high-entropy blobs (~7.5 bits/byte, compressed or packed) and 4bpp tile data (~3.5-4.5), with known copied executable routines |
| `0x08A39820`-`0x08FE1350` | ~5.9 MiB | zero padding |
| `0x08FE1350`-`0x08FFFFFF` | ~124 KiB | `0xFF` padding to the 16 MiB boundary |

The installer at `0x08002768` references the 176-byte image
`[0x08A38A2C,0x08A38ADC)` for copying to `0x03005E78` through the
`SVC 0x0B` wrapper at `0x0814186C`. Under the BIOS CpuSet contract, its
third call copies 88 halfwords. The image contains these complete Thumb
bodies, not one 176-byte function:

| ROM body (exclusive end) | Installed RAM body (exclusive end) | Bytes | Instructions |
|---|---|---:|---:|
| `0x08A38A2C`-`0x08A38A5E` | `0x03005E78`-`0x03005EAA` | 50 | 25 |
| `0x08A38A60`-`0x08A38A9C` | `0x03005EAC`-`0x03005EE8` | 60 | 30 |
| `0x08A38A9C`-`0x08A38ADA` | `0x03005EE8`-`0x03005F26` | 62 | 31 |

Two external zero halfwords complete the copied image. RAM placements are
aliases of these ROM bodies, not additional functions. Installation does not
prove that later RAM writes preserve their bytes. The installer itself owns
80 bytes: 58 code bytes (26 instructions), two internal alignment bytes and
five required literal words. Its return before those literals is not its
complete boundary. The function denominator below `0x08150000` remains
provisional and excludes these later bodies. The byte denominator instead
sums legacy layout segments named `code*`, including late-ROM segments;
those labels do not prove code ownership. Neither denominator establishes
exhaustive whole-game coverage.

Startup chain, walked from the entry point:

```
0x080000C0  ARM   crt0: CPSR/user-mode switch, stack and IRQ vectors, then
                    `ldr r1,[pc,#0x154]; mov lr,pc; bx r1` into Thumb
0x08000254  Thumb  init: hardware setup, table copies, then calls into the
                    function at 0x08000670 and others
0x08000670  Thumb  first "real" game function (117 instructions)
```

## What the analysis found

`5,455` functions — `5,335` Thumb, `120` ARM — and `156,843` bytes of verified
instruction bodies (`77,268` instructions). Median function body is 10
instructions; the largest found is 128. Function boundaries come from a
prologue pattern **plus** a linear walk that must reach a return or a tail
branch, which is what keeps the 4bpp tile data from producing thousands of
fake functions (the byte pair `0xB5xx` looks like `push {rX, lr}` about once
every 300 KiB of tile data).

Per 64 KiB of ROM, verified code density:

```
0x08000000   17.1%   ##########
0x08010000    6.3%   #####
...
0x08140000    8.1%   #####
0x08150000    0.7%          <- falls off a cliff: assets start here
```

## Using it

The analysis needs nothing but Python 3 and capstone, on any OS:

```sh
python -m pip install capstone

python ../fftadecomp-kit/tools/analyze.py baserom.bin .   # ROM -> config/, symbols/, logs/
                                                          # (~10 min, 16 MiB)
python ../fftadecomp-kit/tools/split.py   baserom.bin .   # analysis -> asm/, files/
python ../fftadecomp-kit/tools/rebuild.py .                 # must print: byte for byte
```

`make check` is the same as `rebuild.py`; `make regen` runs all three. Under
WSL/Linux, `../fftadecomp-kit/tools/bootstrap.sh` installs the rest of the toolchain.

### Rebuilding with an assembler

```sh
make rom      # armips asm/ffta.s, then verify against the base ROM
```

The `.incbin` data guarantees every non-code byte is right; the assembly in the
code region is what armips has to re-encode exactly.

## Matching

**The compiler has been identified: agbcc — `gcc 2.9-arm-000512 for Thumb/elf`**
(12 May 2005). Full details, build instructions and the flag study are in
[`docs/toolchain.md`](docs/toolchain.md).

```
agbcc -mthumb-interwork -O2
```

The first seven matches are listed below; the complete, growing catalog is in
`src/` and `docs/match/`. Each is verified by compiling the C and comparing the
entire ELF function symbol against the ROM, including its literal pools:

| address | bytes | what it is |
|---|---|---|
| `0x08017514` | 18 | four byte stores, 4th argument on the stack |
| `0x08011040` | 22 | copies three 16-bit fields and returns a byte at offset `0x1D` |
| `0x080112D4` | 20 | copies three `s16` fields out of a struct |
| `0x08006ADC` | 28 | table slot write + flag clear (u8 index) |
| `0x0801CD4C` | 32 | scatters 4 bytes from the table at `0x02007F10` |
| `0x08017AC4` | 20 | sets flag bit 1 and stores two 32-bit fields |
| `0x0801E68C` | 28 | copies three words from the structure at `0x02007F40` |

```
python ../fftadecomp-kit/tools/match.py 0x08017514   # or: make match ADDR=0x08017514
```

The tool preprocesses (`agbcc` is a raw cc1 and does not run cpp itself),
compiles, assembles, strips, and diffs against the ROM bytes.

To verify that all currently matched C integrates into the full ROM:

```sh
python ../fftadecomp-kit/tools/rebuild.py . --compiled
python ../fftadecomp-kit/tools/rebuild.py . --compiled --output build/ffta-mixed.gba
```

The optional output must not already exist. This is a partial mixed C/ROM build:
verified compiled symbols replace their original ranges, while unmatched code
and data remain original. The tool reports both byte counts and compares the
entire resulting image. Byte-exact integration is not 100% decompilation.

Two findings worth keeping in mind while writing C:

* **The compiler reads stack arguments straight off `sp`** — 286 functions in
  the ROM do this, with no frame pointer. Modern GCC will not.
* **Address constants must go in a variable.** For `func_0801CD4C`, writing
  `((u8 *)0x02007F10)[0x0d]` inline makes the compiler fold every access into
  its own literal-pool entry; a local pointer gives the single load the ROM has.

### Rule for this repo

**Only byte-exact matches, from plausible source, are committed.**

`tools/match.py` puts a function through two gates, and both have to pass:

1. **Bytes.** The entire compiled ELF function, including literal pools, must
   be identical to the ROM. Mode and alignment must agree, relocations must
   be resolved, and a complete return must be verified. The current verifier
   accepts canonical straight-line leaf functions; unsupported control flow
   fails closed until linked CFG verification is available.
2. **Plausibility.** The source must look like something a developer could
   have written. `tools/plausible.py` rejects inline asm, optimisation
   pragmas, dead code, `volatile`, placeholder bodies, steering padding,
   attributes that only affect emission, and comments that admit the code
   exists to steer the compiler.

A function that fails either gate is not a match. Byte-identical output from
implausible source is the *failure* case this rule exists for: it proves the
bytes, not the decompilation. Such a function reports
`IMPLAUSIBLE - bytes match but the source is not code a developer would have
written`, and its report deliberately does not contain the string the CI looks
for.

Anything that fails either gate goes in `Parked/<address>/` with its match
report, until it is fixed — not until a compiler flag is nudged.

### Before you work on a function: reserve it

Agents working in parallel have to claim the address they are on, so the claim
lives as an issue in **fftadecomp-kit** — the ledger is shared, the repo is
not:

```sh
python ../fftadecomp-kit/tools/reserve.py check 0x08011040   # 0 free, 1 taken
python ../fftadecomp-kit/tools/reserve.py claim 0x08011040 --who me --note "..."
python ../fftadecomp-kit/tools/reserve.py claim 0x08011040 0x080112D4 --who me
```

`claim` refuses an address somebody else holds. Reservations are leases: ping
while working, **release when you stop — especially when you conclude a
function cannot be matched**, with `--unmatchable` so the next agent is told to
skip it. Anything quiet for 3 days is auto-released by a workflow.

A batch claim creates one issue after checking every member. Release members
individually with `release ADDRESS --issue NUMBER --who me --reason "..."`;
the issue remains open until its last member is released. Serialize updates
to a batch so one release cannot overwrite another.

### Flags still open

`-O1`, `-O2`, `-O3` and `-Os` all reproduce the four original matched functions; they
only differ on inlining (`-O3` inlines most, `-O1` least). A function that calls
a static helper will pin the level down. `-mthumb-interwork` and "some
optimization enabled" are already established.

## Honest limits of this first pass

* **Function bodies are linear sweeps.** They stop at the first branch or
  return, so a function with internal branches currently shows only its entry
  block; the rest is in `files/code_*.bin`. As you match functions, extend the
  bodies.
* **Literal pools are data gaps**, which is why code and data alternate
  throughout the code region. Turning the `data_*.bin` gaps between functions
  into `.pool` + named constants is the first thing to do per function.
* **A few functions come from jump tables** (overlapping ranges, `endby=linear`),
  and a handful of false positives survive deep in the asset regions. Compare
  against a real disassembler (Ghidra/IDA) when you start a specific area.

## Next steps for an actual decomp

1. **Work through the small functions.** The current matches are all leaf
   functions with no branches. The next ones to take are the other complete
   leaf/straight-line functions listed in `symbols/functions.txt`
   — same shape, same harness, and each one teaches you about struct layouts.
2. **Pin the optimisation level** by finding a function that calls a static
   helper and checking whether the call survives: that separates `-O1` from
   `-O2`/`-Os` from `-O3`.
3. **Set up objdiff** (`cargo install objdiff`) to get per-function progress.
   Note `mips_to_c` does not apply — it only reads MIPS.
4. **Name as you go.** `func_08017514` → whatever it really does, in
   `symbols/ffta.sym` and in the `.global` lines of the asm.
